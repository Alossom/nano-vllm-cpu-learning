# nano-vllm-cpu-learning 性能测试报告

测试日期：2026-11-01。测试版本：`ecddefc5c4a1e36ffc85d65c5ce040d84340cc4d`。
原版基线：仓库父提交 `bb823b3e06983d71485a8e1f23715ebd87d98ef8`。
本次实际读取 WSL 中的项目和真实 Qwen3-0.6B 权重进行测试，测试过程没有修改推理源码。本目录为随后公开归档的测试报告及原始数据。

## 结论

1. **相较原版调度逻辑，有明确的特定场景延迟改善。** 在相同 CPU 模型执行器上，长请求插入时，新增 alternating 策略将已有请求的最大相邻 token 间隔中位数从 2.213 秒降到 0.630 秒，降低 **71.5%**。
2. **未证明相较原版整体推理更快。** 同一对照中新请求首 token 时间增加 **9.2%**；总吞吐差异小、范围重叠。原版完整 GPU 引擎因没有 CUDA 而未测，不能宣称超越其 GPU 性能。
3. **前缀缓存和批处理在当前 CPU 实现中有效。** 256-token 前缀命中使目标请求首 token 时间降低 **93.0%**；相同四个请求批处理的输出吞吐比逐个执行提高 **59.3%**。这属于内部机制收益；原版也有这些机制，不是本项目相较原版独有的优化。
4. **长输入与多请求场景仍落后于 Transformers CPU 基线。** 在对齐 Prefill 批次的比较中，本项目长输入吞吐低于 HF SDPA **18.5%**，四请求吞吐低 **24.3%**。短输入差距较小，不能据此宣称普遍领先。
5. 各重复运行、分块/完整 Prefill、前缀命中/重算、串行/批处理、原版/新增调度策略，以及所测 HF 对照的生成 token 一致性检查全部通过。这里只覆盖报告指定负载，不替代全项目回归测试。

## 环境与测量口径

| 项目 | 实际设置 |
|---|---|
| CPU | Intel Core Ultra 5 336H，WSL 暴露 12 个逻辑 CPU |
| 操作系统 | Windows 主机上的 WSL2 Ubuntu |
| WSL 内存 | 约 15 GiB |
| Python | 3.11.16 |
| PyTorch | 2.14.0+cpu |
| Transformers | 5.16.1 |
| 模型 | 本地 Qwen3-0.6B，596,049,920 个参数 |
| 权重/计算 | CPU float32；未量化、未 torch.compile |
| 线程 | PyTorch intra-op=4，interop=1 |
| CPU 项目 KV Cache | 8 blocks × 256 tokens；预分配张量 448 MiB |
| 生成方式 | Greedy、固定输出数量、忽略 EOS，保证各实现工作量相同 |
| 输入 | 固定随机种子的合法 token ID；32、64、257、513-token 合成负载 |
| 通常输出长度 | 每请求 16 token；动态到达测试 B 为 8 token |
| 重复数 | 普通场景预热 1 次、测量 3 次；交错调度复测每策略预热 1 次、测量 6 次 |
| 总量 | 60 次正式测量，另有 18 次负载预热；算子分析单独进行 |

所有性能表均报告中位数。原始数据包含每次测量及逐轮事件。
吞吐 = 实际生成 token 总数 / 从请求提交至全部完成的时间，**包含 Prefill，不等于纯 Decode token/s**。
TTFT 从请求加入测试引擎至第一个输出产生，包含调度等待；不包括模型加载、Tokenizer、预热、网页/网络开销。
HF 使用显式逐 token 前向循环、KV Cache、`logits_to_keep=1`，避免对全部输入位置计算词表 logits；不是默认 `generate()` 的整体 API 测试。
初次缓存填充的成本不计入随后“前缀命中请求”的计时。

未做 CPU 绑核、主机背景任务隔离、热状态固定或线程数寻优。3/6 次是初步工程测量，不能报告稳定 p99 或统计显著性。
原版/新策略复测交错执行顺序，以减少顺序偏差；HF 对照在独立进程按阶段串行执行。

## 一、与原版调度器的直接对照

使用未经修改的原版 Scheduler、Sequence 和 BlockManager，并通过测试适配器接入相同的 CPU GreedyModelRunner、InputBuilder、TinyCausalLM。
核验这三个原版文件相对父提交没有变更；先用微型模型验证接口兼容，再运行真实权重。
因此，此对照测的是**原版调度和缓存管理路径与新增路径在同一 CPU 后端上的差异**，没有测试原版 CUDA Runner。

工作负载：A 输入 32 token、输出 16；A 完成 Prefill 和一次 Decode 后，提交输入 513 token、输出 8 的 B。每轮 Prefill 预算为 128 token。两策略输入、权重、线程和到达触发条件相同。

| 指标 | 原版 Prefill 优先 | 本项目 alternating | 解释 |
|---|---:|---:|---|
| A 最大相邻 token 间隔 | 2.213 s | 0.630 s | 降低 71.5%，输出停顿明显缩短 |
| A 最大间隔测量范围 | 2.144–2.273 s | 0.602–0.833 s | 6 次复测均显示明显改善 |
| B 首 token 时间 | 2.085 s | 2.277 s | 增加 9.2%，存在公平性取舍 |
| 全部请求完成时间 | 3.564 s | 3.509 s | 中位数略短，不能判定稳定提速 |
| 全部完成时间范围 | 3.484–3.580 s | 3.453–4.046 s | 范围重叠 |
| 总输出吞吐 | 6.734 token/s | 6.840 token/s | 差异小，不作为吞吐改进结论 |

原版会连续处理 B 的几个 Prefill 分块，使 A 暂停输出；alternating 在这些分块之间执行 Decode，让 A 更快得到下一 token，但也推迟 B 完成 Prefill。

初轮独立测试中，同样使用当前 CPU 实现的 prefill_first 与 alternating 对照也呈现相同趋势：A 最大间隔约 2.246 s 对 0.660 s。不过初轮 alternating 的吞吐略低，进一步说明不应将小幅吞吐变化解释为稳定提升。

原版已经实现 chunked prefill、continuous batching、prefix caching 和抢占恢复。这些功能可作为项目能力展示，不能全部列为相较原版新增的性能创新。

## 二、CPU 实现内部机制收益

| 场景 | TTFT | 完成时间 | 输出吞吐 |
|---|---:|---:|---:|
| 单请求 32 输入 + 16 输出 | 0.162 s | 0.952 s | 16.807 token/s |
| 257 输入，128-token 分块，16 输出 | 0.933 s | 1.935 s | 8.267 token/s |
| 257 输入，一次 Prefill，16 输出 | 0.883 s | 1.887 s | 8.481 token/s |
| 257 输入，命中前 256 token，16 输出 | 0.066 s | 1.081 s | 14.807 token/s |
| 4 请求逐个执行，各 64 输入 + 16 输出 | 见下文 | 4.384 s | 14.598 token/s |
| 4 请求批处理，Prefill 总预算 128 | 0.713 s（请求平均） | 2.752 s | 23.252 token/s |
| 4 请求批处理，一次处理全部 256 个输入 | 0.845 s（请求平均） | 2.518 s | 25.420 token/s |

### 前缀缓存

对同一个 257-token 目标请求，预先计算另一个只在最后一 token 不同的请求，使前 256 token 可复用。
随后测量目标请求的生成，与无有效前缀索引的完整计算比较。

- 实际 Prefill 输入：257 → 1 token，跳过 256 token。
- TTFT：0.933 → 0.0657 s，降低 92.96%，首 token 约快 14.20 倍。
- 整个请求完成时间：1.935 → 1.081 s，约快 1.79 倍。
- 生成的全部 16 个 token 一致。
- 不包含建立前缀的首次计算成本；不能把 14.2 倍表述成所有请求或整个生成过程的加速比。
- 此测试比较“命中与不命中”，不是完全移除缓存管理代码的消融。

### 批处理

同样四个独立请求，批处理吞吐为 23.252 token/s，串行为 14.598 token/s，提高 59.3%；总时间减少约 37.2%。

串行场景的每请求 TTFT 从各自实际提交时开始，未包括前面请求占用的时间，因此不能把其平均 0.274 s 与同时提交四请求的 TTFT 直接当作用户排队体验对比。
更公平的收益指标是处理同样四个请求的总时间和总吞吐。
同时提交的四请求实验量化的是 batching 效果；动态插入请求的实验才检验 continuous batching 的调度效果。

### Chunked Prefill

单请求 257-token 输入时，128-token 分块比一次 Prefill：
- TTFT 增加约 5.7%。
- 整个请求完成时间增加约 2.6%。

这说明分块并非自动加速单请求。其价值是提供调度切换机会；在本项目 alternating 策略中，可减少已有请求被长 Prompt 阻塞的时间。
当前 BlockManager 在分配时仍会为请求的现有 token 长度分配所需 block，不能将分块描述为 KV 只按本轮 chunk 申请。

## 三、与 Transformers CPU 的对照

相同模型、精度、线程数、输入和输出长度。长输入一次 Prefill；四请求对照中本项目也一次完成全部 256 个输入，避免 Prefill 批次不同。

| 工作负载 | 本项目吞吐 | HF eager | HF SDPA | 本项目相对 SDPA |
|---|---:|---:|---:|---:|
| 单请求 32 输入 + 16 输出 | 16.807 | 15.349 | 16.127 | +4.2% |
| 单请求 257 输入 + 16 输出 | 8.481 | 9.764 | 10.403 | −18.5% |
| 4 请求，各 64 输入 + 16 输出 | 25.420 | 32.307 | 33.578 | −24.3% |

单位：实际输出 token/s，包含 Prefill。

| 工作负载 | 本项目 TTFT | HF eager TTFT | HF SDPA TTFT |
|---|---:|---:|---:|
| 单请求 32 输入 | 0.162 s | 0.178 s | 0.185 s |
| 单请求 257 输入 | 0.883 s | 0.864 s | 0.826 s |
| 四请求整批 Prefill | 0.845 s | 0.764 s | 0.752 s |

所有这些对照的生成 token 逐一一致。短输入的吞吐差距接近测量波动，不能泛化为本项目优于 Transformers。
HF 是另一个 CPU 参照，不是原版 nano-vLLM。

## 四、内存和算子分析

CPU 实现：8 个 256-token KV block，28 层、8 个 KV head、head_dim=128、float32。
KV 张量预分配 = 2 × 28 × 8 × 256 × 8 × 128 × 4 = **469,762,048 bytes = 448 MiB**。

本项目进程 RSS 高水位约 **4.33 GiB**；HF 约 **4.54 GiB**。
这是包含模型加载和预热的进程历史峰值。各自分配器、权重映射与缓存布局不同，且单进程后续场景沿用历史峰值，不能将差值直接解读为推理显存/内存节省。

单独对 257-token Prefill 和紧接的一轮 Decode 做 CPU profiler 采样；该数据不用于前述性能计时。

| 项目 | Prefill | Decode | 口径 |
|---|---:|---:|---|
| aten::mm | 77.8% | 52.3% | self CPU，线性层/LM Head 等矩阵乘 |
| aten::bmm | 5.5% | 1.3% | self CPU |
| KVCache.read | 0.6% | 8.2% | 含子调用 |
| aten::isfinite | 1.8% | 11.4% | 含子调用，不包括外层 all 的全部成本 |
| LM Head | 0.9% | 12.0% | 含子调用 |

这些比例混合 self 和含子调用口径，**不能相加**，也不是改动后可保证获得的提速比例。
Profiler 仅采样各一轮，包含观测开销，不构成完整瓶颈模型。
源码与采样共同表明：Decode 每层读取上下文 K/V 时有 gather/copy，且 ReferenceAttention 每层扫描 Q/K/V 的有限值，存在可测的额外开销。
Prefill 的主要算子时间仍在线性层矩阵乘；不能认为只换 Attention 就能解决全部性能差距。

## 五、建议的优化顺序

1. **将内部昂贵数值扫描改为可配置的调试检查。** 默认行为如何调整需要另行设计；保留输入、权重加载和错误诊断能力，对开/关做相同负载消融与数值回归。
2. **优化 KVCache 读取与重复构造的索引。** 评估连续 block 的快速路径、预计算位置/槽位及减少不必要复制；注意共享前缀只读语义，不能直接删除复制后破坏调用方隔离。
3. **优化批内 Attention 执行。** 当前逐请求循环计算 Attention；评估 SDPA 或适合不同长度请求的分组执行，继续测试 MHA/GQA/MQA、chunked prefill、非连续 block 与前缀共享。
4. **调优 CPU 矩阵乘与权重布局。** 本轮只有 4 线程；下一轮先做线程/批大小扫描，再考虑融合投影与量化。量化改变精度，应作为单独配置，不能与本次 float32 数据混为同一基线。
5. **把 alternating 升级为可测的延迟目标调度。** 已证实有平滑输出的价值，同时需控制新请求 TTFT 的代价，避免只优化单一指标。

这些是后续候选改动，本轮没有实施或声称已获得对应收益。

## 六、结论适用范围与交付数据

未测试：原版完整 CUDA 引擎、GPU 对 GPU、不同 CPU/线程配置、真实用户到达分布、长时间压力、稳定 p95/p99、能耗、量化、随机采样开销、服务网络和网页响应。
本轮不能证明“CPU 比 GPU 快”“整体超越 nano-vLLM”“生产可用”。
能够支持的表述是：

> 在同一 CPU 后端的指定动态请求负载下，新增交替调度使已有请求的最大 token 间隔中位数降低约 71.5%，代价是新请求 TTFT 增加约 9.2%；当前实现仍有长输入和多请求吞吐优化空间。
